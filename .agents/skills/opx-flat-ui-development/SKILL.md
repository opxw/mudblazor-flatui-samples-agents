# OPX Flat UI development

Use the repository's compiled sample as the behavioral source of truth and the RCL source as the reusable API source of truth. Do not introduce another UI framework.

## Start every task

1. Read repository `RULES.md`, `.agents/RULES.md`, `.agents/KNOWLEDGE.md`, and `.agents/PROMPTING.md` completely.
2. Read [page-registry.md](references/page-registry.md), resolve the prompt to one canonical `PageId`, apply its interaction/state profile from [showcase-behavior-registry.md](references/showcase-behavior-registry.md), then read [sample-source-map.md](references/sample-source-map.md) and select its closest archetype.
3. Open that sample page/layout and every shared component it directly uses.
4. Inspect nearby repository instructions and the current worktree before editing.
5. State the selected `PageId`; state any assumption that materially changes page type, permissions, data ownership, or responsive behavior.

The user may prompt with only a short business job in ordinary language and never needs to supply a `PageId` or behavior profile. Infer PageId, profile, shell, sample, fields/columns, actions, states, spacing, and responsive transformation from `.agents/PROMPTING.md`, repository context, and the canonical registries. Do not ask the user to choose an ID or routine UI mechanics already owned by the mapped profile unless two workflows remain materially different after contextual analysis.

For defect diagnosis, compare the consumer with an unchanged canonical sample on the same supported NuGet version and identify whether the failing behavior is package-owned or host-owned. When package-owned component/API/CSS/JavaScript behavior is proven responsible, write the exact phrase **"bug package"**. When the defect is consumer markup, local CSS, configuration, host service, stale asset, or integration, write **"bug integrasi aplikasi"**. Until that boundary is proven, write **"belum terklasifikasi"** and name the missing evidence; never guess from visual location alone.

## UI/UX requirements analysis

Act as the UI/UX specialist, business analyst, and data analyst for every UI request. Before selecting a component or writing markup, translate the request into:

- the user or role and their primary job-to-be-done;
- information hierarchy, data density, and the most frequent or critical action;
- read-only versus mutation flows, destructive risk, permissions, and confirmation needs;
- host and device context (desktop Web, responsive Web, or MAUI Hybrid), input method, and likely interruption or offline constraints;
- loading, empty, error, disabled, success, unsaved, and recovery states;
- accessibility, keyboard/touch, localization/RTL, and responsive requirements.
- the business objective, decision or transaction the page supports, source and grain of data, dimensions/measures, freshness, comparison period, exception thresholds, and drill-down path when relevant.

When that analysis reveals a material improvement, communicate it proactively as **`Saran UI/UX`** using the contract in `.agents/PROMPTING.md`: observed need/risk, one concrete canonical recommendation, user/business impact, priority (`Wajib`, `Disarankan`, or `Opsional`), and scope/approval boundary. Omit the section when there is no material suggestion. Never use suggestions to override explicit user decisions, invent domain rules, or silently expand the task.

Use that analysis to select one canonical `PageId`, the nearest sample archetype, shell, navigation pattern, shared components, and interaction/state model. For dashboards, include only KPIs that support a named decision, show units/time scope, prioritize exceptions and trends, and provide a path to underlying records. For transactions, preserve lifecycle, validation, authorization, totals, review/confirmation, concurrency, reversal/recovery, and audit boundaries. Prefer the simplest composition that completes the user's job. Do not add dashboards, filters, CRUD, FABs, dialogs, or visualizations merely because the sample offers them. Never invent business formulas, thresholds, statuses, permissions, or live data; state assumptions and keep domain data, authorization, persistence, calculation authority, and integration host-owned.

When two choices would materially change the workflow, data ownership, permissions, or mobile behavior, ask one focused question. Otherwise state the assumptions and briefly explain why the selected archetype and components fit before implementation.

For a layout request, read [layout-decision.md](references/layout-decision.md). Before implementation, provide a concise layout blueprint containing the user/job, selected `PageId` and archetype, shell/navigation, desktop regions and hierarchy, tablet/phone transformation, primary and secondary action placement, essential states, and the UX reason for the choice. When the request supplies enough business intent, decide these details as the UI/UX expert instead of asking the user to design the screen. Ask only when missing information would materially change workflow, ownership, permissions, or platform behavior.

## Adaptive responsive principle

- Treat responsive design as a change in composition and priority, never as uniform desktop scaling. Keep one Blazor codebase/design system while adapting navigation, hierarchy, forms, actions, tables/cards, and secondary information.
- Preserve the established OPX responsive contract: table/desktop above `900px`, responsive/card at `900px` and below, two-column cards at `601-900px`, phone/single-column refinement at `600px` and below, plus documented component-specific boundaries. Default typography ownership and face to Device: `UseAppFontSize=false`, ordinary UI inherits the device/browser system UI font stack and `1rem` accessibility scaling, and no app/custom font is bundled, downloaded, or forced. Manual is an explicit appsettings-backed `16px` size override and does not replace the system family. Package numeric, code, and icon tokens are intentional exceptions. Preserve density independence and high-density touch settings; do not replace them with generic breakpoints or page-local hardcoded type/control scales.
- Treat spacing selection as the package density preference, not a new configuration model. New consumers use `OpxFlatUi:Display:DefaultDensity="Default"`; Compact and Comfortable remain Settings choices and Restore returns to Default. Density changes internal control/table/card/navigation/toolbar rhythm only. Preserve canonical page gutters, positive panel padding, safe areas, widget contracts, and component-specific gaps independently; never add `DefaultSpacing` or page-local density CSS.
- For `NavigationLayout=Bottom`, select the shell from viewport width alone. `FlatAppShell.BottomNavigationMaxWidthPx` defaults to `600`; this template sets it to `900` so tablet and phone use Bottom navigation while the sidebar returns above `900px`. Update during live resize in Web, MAUI Hybrid, and Windows EXE hosts without OS, device-type, user-agent, or MAUI-platform branching.
- Resolve any ordinary user request for Bottom navigation to `DefaultBottomNavigationChildPresentation="Sheet"`. Use the package-owned locked, theme-synchronized recursive sheet for parent/overflow items. Choose `MainView` only when the user explicitly requests that presentation or when implementing its labeled showcase preview; never synthesize a page-local child-navigation sheet.
- Feed Sidebar and Bottom navigation from one recursive `FlatAppShell.NavigationItems` tree when supported. Reserve `Menu` for an intentional custom compatibility override and never maintain equivalent Web/MAUI menu trees.
- Preserve descenders in every Bottom-navigation label with package CSS line-height `1.25` and a `1px` bottom inset. Keep single-line ellipsis and the `60px` bar; do not enlarge the bar or add page/app-local overrides for reusable label geometry.
- Give ordinary content-panel bodies a positive logical horizontal inset: default `padding-inline:14px` on desktop and `12px` at `<=900px`, unless the mapped compiled sample defines another positive value. Never set readable content's left inset to zero. An edge-to-edge table/media shell may use outer `padding:0` only when its immediate readable child states, toolbar, cards, or editor own the positive inset. Use logical properties for RTL. On short landscape viewports keep content scrollable and top-aligned, consolidate same-scope actions, and do not spend a second toolbar on a lone Refresh action.
- Use viewport/container CSS for layout and typography. Do not detect Android/iOS to choose font size or composition; native capability checks are only for platform-owned camera, notifications, safe area, keyboard/IME, lifecycle, and system Back.
- When an Android MAUI host must visually merge its status bar with the AppBar, use `samples/Opx.MudBlazor.FlatUi.MauiHost.Sample`: keep the native status bar transparent through host-owned `CommunityToolkit.Maui` `StatusBarBehavior`, measure the actual `WindowInsets` top value, extend the AppBar to `60px + inset` while keeping controls in the lower `60px`, and update contrast-aware icons on Light/Dark/Auto, system-theme, and palette events. Never guess a fixed inset or move this native adapter into the reusable package.
- For a complete MAUI showroom or performance comparison, use the same host's synchronized catalog rather than recreating pages. Run its sync script and page-sync audit, keep PageIds/routes identical to the Web sample, and use PageId `opx.page.reference.maui-performance` for current-process startup/route-render samples. Only repeated Release measurements on the named device are performance evidence.
- Keep primary mobile content readable and touchable, defer secondary facts, stack long forms, and place critical actions within easy reach. Keep desktop compact, multi-column, and data-oriented. Convert unsuitable tables to equivalent shared-state cards/lists rather than compressing columns into unreadable content.
- Prefer one Razor composition when semantics remain equivalent; use dedicated desktop/mobile templates only when hierarchy changes, with one query, selection, permission, loading, validation, and mutation state.
- For every page change, verify representative desktop, tablet/responsive, and phone widths plus no-reload desktop -> responsive -> desktop resize. Include Light/Dark/Auto, browser text scaling, keyboard focus, touch geometry, scroll ownership, and horizontal-overflow checks. Native MAUI claims still require emulator/device evidence.

## Consumer contract gate

Package-first reuse is mandatory. Before writing a new component, page-local markup, CSS/JavaScript behavior, or host adapter, inspect the supported NuGet public API, the resolved PageId's compiled canonical sample, and—only when necessary to confirm ownership—the package source/API map. Use an existing public component, option, callback, service seam, or asset exactly when it fits. Never duplicate package behavior in the consumer, fork package CSS/JavaScript, or replace the public `PackageReference` with a package-source `ProjectReference`.

If no fitting capability is verified, classify ownership before recommending implementation. A domain-neutral reusable gap is a decision-ready package suggestion; domain data, authorization, persistence, integrations, and platform-native behavior remain host-owned seams. State the observed need, proposed public API/component or host seam, user/business impact, priority (`Wajib`, `Disarankan`, or `Opsional`), compatibility/migration/testing/release boundary, and whether approval is required. Do not change or publish the package unless the user explicitly authorizes it. If package availability or ownership remains uncertain, say `belum terklasifikasi` and name the evidence still needed.

- When a prompt asks for the same, exact, canonical, source-of-truth, or sample-matching UI, read [exact-sample-mode.md](references/exact-sample-mode.md) and activate Exact Sample Mode. Start from a generated template and the mapped sample file, never from a visual approximation. Establish an unchanged canonical baseline with the matching audit's `-ExactSample` switch before wiring host data or services; then preserve its structural/visual contract while replacing only host-owned content and integration seams.

- Create new Blazor Web consumers with the repository `opx-flatui-web` `dotnet new` template instead of reconstructing the host manually.
- Create new Android/iOS Blazor Hybrid consumers with `dotnet new opx-flatui-maui`. Preserve `flat-ui.mobile.contract.json`, package-mode references, CommunityToolkit and `StatusBarBehavior`, the host-owned resolved AppBar/status-bar bridge, Device typography, Bottom navigation through `900px`, native no-bounce handling, textbox-only selection, static-to-interactive `Memuat` handoff, Settings, and root-before-Router authorization validation. Run `scripts/audit_maui_consumer.ps1` plus an Android Release build. Treat iOS build/runtime, lifecycle, safe-area, IME, selection, status-bar, and bounce behavior as unverified until checked on macOS with an iOS simulator/device.
- Keep `flat-ui.contract.json` and `flat-ui.contract.schema.json` in the consumer root. The current schema `3.1` pins `Opx.MudBlazor.FlatUi` `2.0.20` and `MudBlazor` `9.9.0`; treat these versions, baseline `PageId`, archetype, Light default theme, built-in `fluent-blue` default palette, CRUD terminology, Device/Manual font ownership, responsive breakpoint, native-mobile deployment requirements, and root-before-Router startup access gate as one versioned contract. The checking branch initializes display preferences, resolves the current theme/palette, and renders `FlatSessionRestore` with `OpxFlatUi:Reconnect:StartupTitle`/`StartupMessage` inside loading-only `FlatMudProviders`; `Router` is created only after validation, and normal layout providers remain separate so theme/palette preview is preserved without nesting.
- Emit exactly one `<!-- Powered by opx (github.com/opxw) -->` immediately inside the host document `<body>` before `RootStartupGate` through an explicit `MarkupString`. A literal HTML comment in a Razor file is removed during compilation, and a Razor comment is also absent from runtime output; verify the initial HTTP response for more than one route.
- Keep the initialized admin shell complete. `MainLayout.razor` must mount a functional sidebar and expose Settings from the AppBar `MoreVert` menu; Settings opens the dedicated Application preferences modal with Light, Dark / Night, and Auto. Start the sidebar from `SampleSidebarMenu.razor` with Dashboard `/`, the default sample groups, search, and active-route expansion. Keep the seeded user block ordered as avatar, identity copy, then a fixed-size Logout icon aligned at the right edge on desktop and responsive drawers with accessible name `Logout`; the host owns its real session behavior. Domain menu records may be adapted later, but neither Settings nor functional sidebar navigation may be removed.
- Treat dashboard status/quick-access content, user-summary rows, current-user identity/avatar/role, logout/session behavior, and final business menu labels/routes/permissions as consumer-owned. They may appear as explicit sample data but are not contract requirements and must not be copied as real domain or identity state.
- Keep consumers on public NuGet `PackageReference`; reject a source `ProjectReference` to Opx.MudBlazor.FlatUi.
- Start each generated consumer through `run-clean.ps1`. It must resolve its own single project, remove only exact project-local `bin` and `obj`, restore through `NuGet.Config`, and run with `--no-restore`; use `-PrepareOnly` for non-running validation.
- Load reusable CSS only from `_content/Opx.MudBlazor.FlatUi/opx-flat-ui.css` and MudBlazor CSS only from its `_content` asset. Reject local copies of either package stylesheet, additional UI-framework CSS, and Bootstrap files in generated output. Keep the initial `wwwroot/app.css` byte-identical to the source sample and limited to sample/domain composition, not reusable-component overrides.
- Before accepting consumer work, run `scripts/audit_flat_ui_consumer.ps1 -ProjectPath <project-or-directory>`, then restore/build Release and verify representative desktop/mobile Light/Dark rendering.
- Adapt branding, wording, data, authorization, and domain integration. Do not silently replace the mapped composition, responsive behavior, theme tokens, loading, modal, toolbar, grid, or FAB contracts.

## Choose the implementation surface

- For dynamic/autoload navigation records shaped as `MenuText`, `Id`, `ParentId`, `Url`, and `Icon`, select PageId `opx.page.reference.dynamic-menu`, use `FlatDynamicMenu`, and reuse `FlatDynamicMenuBuilder.ToNavigationItems` for horizontal/Bottom navigation. Keep arbitrary-depth hierarchy validation/presentation in the library, while endpoint authentication, authorization filtering, tenancy, ordering, localization, caching, retries, and route permission enforcement remain host-owned. Never treat menu visibility as authorization.
- For ERP transaction documents, large entity lookup, money/quantity/UOM, journal balance, reconciliation, planning, lifecycle, or background-operation UI, select PageId `opx.page.erp.toolkit` and compose the shared ERP components from `ErpToolkit.razor`. Keep fiscal periods, posting, tax/discount, UOM conversion, stock/lot/serial traceability, matching authority, capacity rules, durable jobs, authorization, audit, concurrency, and persistence host-owned.
- Render `FlatEntityLookup<TItem>` in the shared medium modal on desktop/wide tablet and the mandatory fullscreen modal on mobile. Use its `GridColumnDefinition` table-grid contract: each header only toggles ASC/DESC, search filters only the active sorted column whose label remains visible, and the search input receives focus every time the lookup opens. Route unmodified letter/number typing from another focused lookup control into search and return focus there; never intercept Ctrl/Alt/Meta shortcuts or duplicate events already originating from the search input. Use shared supporting typography for search/record values and metadata typography for headers/descriptions; below `900px` apply bounded responsive font sizing without shrinking input, row, checkbox, or action touch geometry. Render the closed trigger's selected/content value at normal `400` weight and slightly below supporting size instead of bold. Keep formatted/numeric alignment, dotted row/cell separators, color plus check selection, compatible `ItemText`/`ItemDescription` fallback columns, and the result grid as the only internal scroller.
- Bind lookup `Items` as `IEnumerable<TItem>` so host arrays, lists, `ICollection<T>`, observable collections, and materialized projections are accepted directly. Keep remote loading, authorization, query limits, paging, collection change notification, and API failures in the host; never send an unbounded/live database query into the component.
- Set lookup `ItemKey` whenever API refreshes may replace object instances. For checkbox lookup use `MultiSelect`, bind `SelectedItems`, and consume `ItemsSelected` as the exact confirmed list canonicalized against the current `Items` snapshot. Empty selection is a valid clear result; business-required validation remains host-owned.

- Compose public career portals under `WebsiteLayout`, with search hero, process, categories, jobs, employers, and CTA. Do not reuse the admin shell or claim live recruiting integrations; host owns vacancies, candidates, resumes, consent, workflow, and delivery.

- Use `FlatAccordion`/`FlatAccordionItem` for reusable disclosure groups. Preserve textual accessible titles and full-header interaction when icons are hidden; default to one open item and opt into Multiple or Flush deliberately.

- Add shared page composition and domain examples under `samples/Opx.MudBlazor.FlatUi.Showcase`; executable hosts keep only runtime shell/adapters and native-only diagnostics.
- Add or change `src/Opx.MudBlazor.FlatUi` only for domain-neutral reusable behavior.
- Extend an existing shared component before duplicating its markup in several pages.
- Keep services, authorization, persistence, API clients, and native platform adapters owned by the host through explicit interfaces/callbacks.
- Treat `wwwroot/opx-flat-ui.js` as the only JavaScript source to edit. Release/Pack generates `opx-flat-ui.min.js` through the pinned repository toolchain. Bind `FlatAssetOptions`; Debug must select source and Release defaults to minified while allowing an explicit appsettings override.

## Build a page from a sample

1. Copy the structural pattern, not the sample's business text or records.
2. Preserve the registry's stable `PageId`, or allocate a unique `opx.page.<area>.<purpose>` ID for a new concept and register its canonical name, route, cues, shell/archetype, and source in `page-registry.md`.
3. Add an exact `@page` route and update route-aware AppBar title/search/navigation sources.
4. Keep operational pages free of duplicate title/description blocks unless explicitly requested. Preserve the shared AppBar AppName/PageTitle proportions near `12px`/`11px` at the Manual `16px` baseline, with bold/regular hierarchy unchanged by density presets. Keep the operational AppBar at `60px` and vertically center its `40px` hamburger with equal `10px` top/bottom gaps.
5. Use `FlatPage`, shared toolbar actions, desktop table, responsive cards, shared pager/query state, and the correct FAB/no-FAB contract.
6. Use shared modal, processing, message-box, settings, notification, and reconnect components instead of page-local alternatives. For an authentication-enabled host, read [session-authorization-bootstrap.md](references/session-authorization-bootstrap.md). Mount `RootStartupGate` from the app root and use `FlatSessionRestore` inside a loading-only `FlatMudProviders` branch as the only rendered surface while a single-flight host check reads an untrusted saved-session hint and validates it. Do not create `Router` or render/flash `MainLayout` before validation, including on anonymous routes; remove the temporary provider branch before the routed layout mounts. Update authentication state first, then render protected routes for a valid result; clear stale state and show Login for missing, invalid, expired, or failed validation. Server/API authorization remains authoritative. `InlinePreview` is showroom-only.
7. Keep all field controls dense and theme synchronized; include disabled, loading, empty, error, and narrow viewport states. Make an outlined field container own one continuous theme-resolved surface across its value and adornment areas, including autofill; keep adornment wrappers, glyphs, and icon buttons transparent, borderless, and shadowless over that shared surface without changing unrelated icon buttons. On focus, use one softened-Primary one-pixel outlined border with no fieldset shadow or second native-input-slot outline, including toolbar/grid search and composite lookup search fields, while preserving established floating-label color and geometry.
8. Establish application metadata and Login branding during initial host scaffolding, before feature-page development. Bind typed `OpxFlatUi:Application` options and seed `AppName`, `CompanyName`, `Author` (default `opx`), copyright, `LoginBrandBackgroundColor`, `LoginBrandBackgroundImageUrl`, `LoginBrandOverlayColor`, and `LoginBrandOverlayOpacity` in appsettings. Render `ApplicationOptions.ResolvedAuthor` once as `<meta name="author">` in the host document `<head>` so every route inherits it; do not repeat metadata in individual pages. Treat both `Logo` and `LogoUrl` as optional; omit the logo wrapper and reserved gap when neither resolves, and keep a configured logo compact. Validate colors and opacity in the library, allow only relative/HTTP(S) image URLs, and render images as `<img>` instead of raw configured CSS. Follow the operational split desktop/mobile composition, omit the duplicate top identity row, lock fields during a single-flight submit, omit static security/sample banners below the form, and show required/invalid credential feedback through the shared Error MessageBox with generic wording. Do not import or imply the reference application's live auth/session contract.
9. Give Not Found content standard page gutters and map unknown routes to the AppBar PageTitle `Not found`.
10. Mark Login/auth password controls with a show/hide action using `opx-password-visibility-field`; keep the eye icon white in resolved Dark/Night and `#212529` in resolved Light regardless of whether the input currently renders as password or text.
11. Preserve English reusable/sample defaults and copyright headers.

## CRUD and data rules

- Use `Edit` as the canonical visible label, editor-title verb, tooltip, and accessible action name for CRUD edit operations. Do not use `Ubah` for this action in the template or generated consumer.
- Configure the standard CRUD create action once through `FlatPage.PrimaryActionVisible`, `PrimaryActionLabel`, `PrimaryActionIcon`, `PrimaryActionAriaLabel`, and `OnPrimaryAction`. Let `FlatPage` render the Filled desktop button above `900px` and the icon-only FAB at `900px` and below; do not pair the automatic API with manual `HeaderActions` or `MobilePrimaryAction` markup.
- Resolve every mobile FAB from typed `OpxFlatUi:Display:DefaultFabShape`: `Circle` is the default/fallback and `Square` is zero-radius. Use `FlatFab.Shape` only for a deliberate local override, while preserving icon-only dimensions, safe-area/bottom-nav offset, no shadow, disabled contrast, and accessible text.
- Render button labels at global normal `400` weight in administrative, auth, website, dialog, popover, snackbar, and FAB surfaces. Preserve action hierarchy through semantic color, border, surface, icon, and disabled contrast rather than bold text.
- Keep `mud-button-text-inherit` genuinely inherited. Do not apply the package semantic button-tone override to those controls; portal widgets such as DatePicker toolbar year/date actions must use their enclosing toolbar foreground in Light, Dark/Night, and Auto.
- Keep filter/search/sort/paging state shared between desktop and mobile views. Table-grid filters default to the `GridColumnDefinition` contract: pass the same `Columns` collection and exact `GridViewState` to `FlatDataGrid` and `MobileGridFilterSheet`, and derive toolbar Filter visibility from whether any column has `FilterEnabled=true`. Do not duplicate mobile filter metadata/state; clear stale criteria when columns are disabled or removed. Render desktop header filter controls and native option menus at compact readable 11px with normal `400` weight and no inherited uppercase/bold styling; keep mobile filter-sheet typography independently touch-scaled. Keep numeric header inputs semantic but hide native spin buttons; focus is one softened-Primary one-pixel border with no secondary outline or shadow.
- Size reusable data-grid columns with `WidthPercent` for proportional layouts or `WidthPx` for fixed geometry; pixels win when both are set. Enable `WordWrap` only for columns with long text; keep its default false, and top-align all cells when any column wraps so short values align to the wrapped first line. Let `FlatDataGrid` infer numeric public properties or declare `ValueKind`/`Format`, use `ValueSelector` for non-property keys, and consume `FlatGridCellContext.FormattedValue` in custom cells. Numeric headers/cells stay right-aligned; numeric cell values use the shared monospace numeric stack with tabular digits and registered `FlatLocalizationOptions`, while header labels retain the normal UI font. Infer default precision from the CLR type: integral types and nullable integral types use `#,##0`; decimal/floating-point types use the configured decimal format. Never add synthetic decimal digits to an integer field unless explicitly configured by the host. Equivalent mobile cards reuse `FlatValueFormatter`.
- Render reusable grid/card statuses with `FlatStatusChip`: use a solid semantic flat background, readable foreground, square corners, no border/shadow, and no decorative bullet. Keep visible status text or an accessible label so state is not encoded by color alone. For an edge-attached mobile status label, add the opt-in `mobile-card-edge-tag` modifier to `mobile-card` and keep the chip as the direct header child; use a fixed responsive width with an exact one-pixel top/right border overlap, preserve reserved title space, compact two-line wrapping, and zero document overflow.
- Keep cards, panels, inputs, dialogs, popovers, snackbars, menus, grids, toolbars, and reusable workspaces square. Ordinary buttons default to `7px` through shared `DefaultRoundedSizePx` (`0-12`); the package also uses it for bottom-sheet top corners. Reject page-local rounded overrides. Semantic circles and FAB shape are separate contracts.
- For widgets, select PageId `opx.page.reference.widgets`, read `Widgets.razor` and `docs/WIDGETS.md`, and keep spacing container-owned. Use `12px` grid gap on desktop and `10px` at `<=600px`; keep each widget at `margin:0`. Preserve body `12px`, header `9px 12px`, footer `8px 12px`, section `18px` desktop/`16px` mobile, heading-bottom `8px`, action metric `13px` desktop/`12px` mobile, compact metric `13px`, and lower-grid top `12px` desktop/`10px` mobile. Do not stack widget margin on parent gap or duplicate padding across the same boundary.
- When an accepted UI or development contract changes, keep the executable `/development-rules` sample summary synchronized with the canonical rules, this skill, page registry, and source map.
- Keep one default-collapsed responsive `Sample code` disclosure available on every sample route through shared layout-level `SamplePageUsage`. Add an archetype-specific copy-ready snippet for reusable concepts and retain the exact route-aware `FlatPage` fallback; do not paste duplicate panels into every Razor page or remove richer local usage examples.
- Bind reusable paging defaults from `OpxFlatUi:Grid` into `FlatGridOptions`, register the options with the host, and initialize each page's `GridViewState` from them before the first local/API load. Preserve `SetPageSize(...)` and `FlatPager.PageSizes` for intentional page-specific overrides. Keep the native page-size select focus as exactly one softened-Primary one-pixel border, with no outer outline, shadow, or double box.
- Hide Filter when no actionable filter UI exists. Keep import/export/download/refresh/custom actions icon-only in one toolbar row. On mobile toolbars with at least two actions and `.module-search`, render a transparent inline utility toggle in the search placeholder/adornment area: Apps/action-grid while collapsed and Close while expanded, never a combo-box-like chevron or overflow menu. Default the action row to collapsed/hidden through `MobileToolbarActionsExpandedByDefault=false`; overlay and vertically center the complete toggle touch target against the rendered search border box, reserve input padding for it, and keep the expanded action row below. A collapsed row consumes no extra vertical space. Opt into an initially expanded row only for a deliberate page requirement.
- Keep one scroll owner per desktop grid: `FlatDataGrid` provides the bounded vertical/horizontal region, while toolbar and pager stay fixed. A custom direct `div` host under `.module-panel` is supported without a package-specific class name; it must resolve shrinkable on desktop and disappear when the equivalent mobile grid is active. Do not add a competing active wrapper scroller; verify `scrollHeight > clientHeight` and `scrollWidth > clientWidth` cases with `overflow:auto` and visible theme-synchronized scrollbars, including while a modal locks document scrolling. Use normal scrollbar width and a clearly contrasted theme-resolved thumb on both axes; do not use a thin border-colored thumb that appears absent in Dark/Night. Repeat that verification after a no-reload desktop -> tablet/mobile -> desktop resize cycle and after changing viewport height.
- Keep upload, showcase, documentation, and long-form pages in natural document flow. Do not wrap them in fixed-height `.module-panel` overflow; bounded internal scrolling belongs only to grids and intentional workspaces.
- For bounded `FlatModelCrud` tablet/mobile cards, keep `.flat-model-crud-mobile` as the single internal vertical scroll owner, with toolbar and pager fixed outside it. Reuse the theme-synchronized grid scrollbar and verify overflow plus zero document-level horizontal drift after live resize.
- Bind each `FlatPage` initial empty request to `InitialLoading`. Let `FlatPageKind` choose the default skeleton (`Module` grid, `CrudForm`/`Settings` form, `Dashboard` dashboard, other kinds list/detail); use `SkeletonTemplate`, count overrides, or `LoadingContent` only when automatic geometry needs refinement.
