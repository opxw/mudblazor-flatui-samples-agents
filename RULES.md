## Page and AppBar

- Every routed sample page has one stable canonical `PageId` registered in `.agents/skills/opx-flat-ui-development/references/page-registry.md`. Keep `PageId`, route, Razor component, AppBar `PageTitle`, and permission keys conceptually separate. Resolve page requests through that registry before selecting an archetype; new routes must add a unique `opx.page.<area>.<purpose>` entry in the same change.
- Public career/marketing pages use the dedicated website shell, not the admin AppBar/sidebar. A Job Landing combines search hero, process, categories, accessible job results, employer proof, and CTA; collapse progressively to one column without document overflow. Vacancy search, applicants, resume security, consent, workflow, analytics, delivery, retention, and persistence remain host-owned.

- Use `FlatAccordion`/`FlatAccordionItem` for disclosure groups. Default mode has one open item; set `Multiple=true` only for deliberate side-by-side comparison. Use Flush only inside an existing bounded container. Leading and toggle icons are optional, but every item retains a textual title, full-header keyboard/touch action, `aria-expanded`, disabled contrast, and Light/Dark parity. Loading, authorization, persistence, and content security remain host-owned.

- Row 1 is `AppName`; row 2 is the route-aware `PageTitle`. `AppName` is compact and bold, while `PageTitle` is compact and regular. At the `14.5px` baseline, use approximately `11px` for AppName and `10px` for PageTitle; density changes must not silently shrink either line.
- Operational pages have no duplicate visible title or description by default. Use the AppBar title and render the content panel directly.
- The 2px AppBar loading line reacts to real route/query changes and shared operations. Ignore same-URL history events used only by modal Back interception, so modal open/close never flashes route loading.
- Convert route/menu names to readable titles, for example `Operasional-CrudAsset` becomes `Operasional - Crud Asset`.
- The hamburger keeps the reference behavior and spacing. Mobile/tablet drawers close when the user clicks outside; desktop drawers remain persistent.
- Sidebar leaf links and group titles may include `FlatNavigationBadge` for a short status/count. Use `MudNavGroup.TitleContent` for a parent badge while retaining `Title` for its accessible label. Badges stay compact, use semantic colors, support a labeled dot mode, truncate instead of widening the drawer, and must not move the established icon, label, connector, or expand-chevron coordinates.
- Dynamic navigation uses `FlatDynamicMenuItem(MenuText, Id, ParentId, Url, Icon)` and `FlatDynamicMenu`. Build arbitrary-depth hierarchy case-insensitively, reject missing/duplicate IDs, missing labels, unknown/self parents, and cycles, expand active ancestors, and keep search recursive without changing row geometry. Use `FlatDynamicMenuBuilder.ToNavigationItems` for horizontal Web and Bottom mobile parity. Loading is cancellable/reloadable; endpoint authentication, authorization filtering, ordering, localization, tenancy, caching, retries, and route permission enforcement remain host-owned. Menu visibility is never authorization.
- Structural selectors in Email and other templates must target an explicit copy/content class, not every direct `span`, when a child component such as `FlatProfileAvatar` also renders a span root. Preserve the avatar's grid centering, fixed size, overflow clipping, and full initials/image visibility. Every email-list row must keep sender, subject, and preview on one full-width content track: unread state, timestamp length, attachment, and star metadata may not shift its text start position. Keep at least a `14px` content gutter from the row edge and `6px` after the star action so unread dots, selected rails, and actions never touch the border.
- Chart samples use real `MudChart` components. Keep `/charts` synchronized with every `ChartType` in the pinned MudBlazor dependency, provide expandable copy-ready Razor for each standard and specialized data contract, and verify chart/code overflow at desktop/mobile widths in Light and Dark/Night.
- Sidebar leaf links and group titles may include `FlatNavigationBadge` for a short status/count. Use `MudNavGroup.TitleContent` for a parent badge while retaining `Title` for its accessible label. Badges stay compact, use semantic colors, support a labeled dot mode, truncate instead of widening the drawer, and must not move the established icon, label, connector, or expand-chevron coordinates.

## Reporting

- Operational reports use `FlatOperationalReportViewer<TItem>` with compact parameters, KPI, grouped desktop rows, explicit subtotal/grand total, row drill-down, and equivalent grouped mobile cards. Refresh, print, and PDF/Excel/CSV generation remain host-owned callbacks; report permissions, scheduling, storage, and delivery are never inferred from UI visibility.
- Pivot analysis uses `FlatPivotGrid<TItem>` with typed host-owned row/column/value selectors, explicit Sum/Count/Average/Minimum/Maximum aggregation, optional row/column totals, and exact source items in cell drill-down results. Desktop owns one internally scrolling sticky matrix; at `900px` and below render equivalent cards with no document overflow and move multi-field analysis controls into the shared filter `BottomSheet` opened by one icon-only header action. Copy committed state when the sheet opens, apply all dimensions atomically, and discard pending changes on close/backdrop/swipe. Keep the desktop configuration panel padded `8px 10px` inside its border, controls at zero outer margin, and an `8px` inline gap so outlined fields do not touch the panel boundary. Pivot headings, labels, totals, and values must use compact ratios of `--opx-ui-font-size`, with a smaller mobile ratio at `600px` and below; they must not inherit the full body size or use fixed pixels. The host owns authorization, complete-dataset/server aggregation, calculated-field semantics, export, persistence, and OLAP/database integration.
- `1.2.0` Advanced Pivot adds typed Rows/Columns/Values placement, multiple measures, label/grand-total sort, hierarchical expansion, percentage-of-total modes, per-user saved views, a cancellation-aware server aggregation contract, and host-owned export callbacks. These are additive roadmap APIs and must not be simulated by silently changing the `1.1.0` single-measure contract.
- Grid Preferences uses a compact two-row mobile record at `700px` and below: visibility, shrinkable column label, and ordering controls share the first row; width and pin controls share the second row. Assign explicit grid areas to the MudBlazor wrappers, normalize dense field margins, keep one solid outer record divider, and never rely on implicit placement or direct-child assumptions.

Audit Trail/Diff renders host-supplied immutable-event facts without inventing audit guarantees. ## Grid and CRUD

- Put search, filter, refresh, import, export, download, print, and custom grid actions in the panel toolbar.
- Toolbar actions are icon-only, borderless/flat, individually visible or hidden, and remain on one line. Text stays in `aria-label` and `title`.
- On responsive/mobile toolbars with at least two actions, provide one very small chevron that collapses/expands the whole icon-action row. Default to expanded, preserve `aria-expanded` and explicit Show/Hide labels, never collapse the full-width search/filter text field, and always keep actions visible on desktop. The reusable behavior remains optional through `MobileToolbarActionsCollapsible` and configurable through `MobileToolbarActionsExpandedByDefault`.
- Hide the toolbar Filter button when the grid has no actionable filter UI. `FlatPage` renders it only when `FilterVisible`/`FilterEnabled` resolves to true and `OnFilter` has a real delegate. Inline search alone does not justify a separate Filter button.
- Default grid filters follow the table-column contract. The desktop grid and responsive filter sheet must receive the same `GridColumnDefinition` collection and exact `GridViewState` instance; derive toolbar Filter visibility from whether any column has `FilterEnabled=true`. Preserve criteria across breakpoints, reset paging when criteria change, and clear stale criteria when a filterable column is disabled or removed. Do not create separate mobile filter metadata or state.
- Data-grid columns may use `WidthPercent` for responsive proportional sizing or `WidthPx` for an intentional fixed width; `WidthPx` wins when both are set. Numeric properties/columns are right-aligned with tabular digits and formatted through registered `FlatLocalizationOptions`; use explicit `ValueKind`/`Format` and `ValueSelector` for currency or keys that do not match a public model property. Custom cells consume `FlatGridCellContext.FormattedValue`, and equivalent mobile cards use `FlatValueFormatter` so localization never diverges across breakpoints.
- Use the opt-in `mobile-card-edge-tag` modifier when a mobile grid status should read as a tag attached to the card's right border. Place it close to the upper header edge, hide the decorative status bullet in edge-tag mode, reserve header space so the tag never overlaps title metadata, allow compact two-line labels, keep every corner square, and preserve zero document overflow. Do not globally convert ordinary table/card status pills.
- Keep the shared visual language square: cards, panels, inputs, selects, buttons, dialogs, popovers, snackbars, menus, grids, toolbars, sheets, and reusable workspaces use `border-radius: 0` in admin, auth, and website shells. Only shapes with semantic meaning or identity—avatars, radio controls, status/typing dots, circular progress/spinners, and calendar day markers—remain circular. Do not reintroduce page-scoped rounded surfaces.
- Do not reserve `BeforePanel`, `.page-actions-only`, a page heading, or an AppBar row for operational grid actions.
- A writable page exposes at most one create action in a viewport. Standard CRUD pages configure `FlatPage` once through `PrimaryActionVisible`, `PrimaryActionLabel`, `PrimaryActionIcon`, `PrimaryActionAriaLabel`, and `OnPrimaryAction`; the component automatically renders a Filled desktop button above `900px` and an icon-only mobile FAB at `900px` and below. Do not duplicate that action through `HeaderActions` or `MobilePrimaryAction`. Manual slots remain only for specialized layouts and must still be mutually exclusive.
- Mobile FABs are icon-only, five percent smaller than the original reference size, and have no shadow.
- A genuinely read-only page has no Add, Edit, Delete, or create FAB. Use `ReadOnlySource` only for that case; do not label mutable in-memory CRUD as read-only.
- Desktop grid and responsive cards share search, sort, filter, paging, selection, and permission state.
- Every reusable page built with `FlatPage` binds its initial empty request to `InitialLoading`. The page automatically selects a responsive skeleton from `FlatPageKind` (`Module` = grid, `CrudForm`/`Settings` = form, `Dashboard` = dashboard, and other kinds = list/detail). Use `SkeletonTemplate` only when the automatic mapping is not representative, `LoadingContent` for genuinely custom geometry, and `SkeletonEnabled="false"` only for a documented exception. Global defaults belong in `OpxFlatUi:Loading`.
- Skeletons are initial-empty-state feedback only. Match grid columns and responsive card fields to the final layout so loading does not shift geometry. Keep existing content visible during refresh, sort, filter, paging, and CRUD reloads; use the AppBar loading line for those subsequent operations.
- Inline editable grids use `FlatEditableGrid<TItem>` with one isolated inline Add/Edit draft at a time. `CloneItem` must not mutate the source row. Prefer `SaveRow` returning `FlatGridEditResult<TItem>` so the host/API can return the canonical persisted row, including generated ID/version values; legacy `SaveItem` remains compatible. Every Create/Update/Delete success, failure, validation failure, and cancellation emits `RowResult` with the exact affected row and operation. Cancel discards the draft, and destructive actions use explicit confirmation. The host owns authorization, API/database persistence, concurrency, idempotency, collection mutation, and query-preserving refresh. Standard pages trigger Add through `FlatPage.PrimaryAction*`; use the grid Add toolbar only for embedded grids without a page primary action. At `900px` and below use equivalent editor cards.
- For ordinary flat DTO CRUD generated from a model, use `FlatModelCrud<TItem>` and `FlatModelForm<TItem>`. Derive default labels, order, visibility, editor kind, and validation from DataAnnotations, while allowing explicit typed field metadata to override reflection. Use `FlatModelFieldKind.SearchComboBox` with local `Options` or cancellable `SearchOptionsAsync` for searchable lookups. Use per-field `EditorTemplate` for any other visual editor; it overrides only that field, while the existing form-level `FieldTemplate` remains the fallback for explicit image fields. Keep API calls, authorization, query bounds, business validation, canonical saved rows, collection mutation/reload, concurrency, confirmation, and audit host-owned. Standard pages set `AddVisible=false` and invoke `BeginCreateAsync` from `FlatPage`; embedded CRUD may show local Add. Cancel never mutates source or reloads the caller; successful save/delete emits exact `RowResult` and `Changed`.
- In Auto CRUD forms, render modal single/multi lookup as explicit `FlatModelFieldKind.Custom` fields through the shared `FieldTemplate`, using `FlatEntityLookup<TLookup>` with a stable `ItemKey`. The host maps selected records to model key fields and calls `NotifyChanged`; do not place business collections or persistence inside `FlatModelForm`.
- Nested lookup/message modals inside an editor must not create nested HTML forms. Render nested modal content form-less and let browser Back/history handling target only the topmost active modal; closing the child must leave the parent editor and its draft state open.
- For visual generated-form layout requests, use PageId `opx.page.reference.model-form-designer` and `FlatModelFormDesigner<TItem>`. Reorder through drag/drop plus Move up/down alternatives, preview the exact `FlatModelForm`, and return normalized `FlatModelFormLayoutDefinition` state. Every native, searchable-combo, image, and per-field custom visual editor participates in the same stable-key layout wrapper, so visibility/span/class/padding/margin and desktop/mobile live preview apply consistently. Apply the same layout through `FlatModelForm.Layout` or `FlatModelCrud.FormLayout`. Accept only validated CSS class tokens and bounded numeric spacing; never accept raw CSS/HTML/script. Authorization, class allowlists, per-user/tenant persistence, versioning, concurrency, and audit remain host-owned. Visual emphasis classes may add a restrained rail/keyline, but must leave the wrapper transparent and preserve the generated control's theme surface.
- Do not infer image upload from string or byte-array model properties. Declare `FlatModelFieldKind.ImageUpload`, render `FlatImageUpload` through the typed `FieldTemplate`, and call `FlatModelFieldTemplateContext.NotifyChanged` only after the draft/media result actually changes.
- Generated Auto CRUD text, number, date, select, and multiline controls use an outlined floating label by default. Derive the caption from field `Label`/`Display(Name)` and retain `Placeholder`/`Display(Prompt)` as the optional in-control hint; do not duplicate an external label. Required markers float with the caption, while Boolean checkboxes keep their accessible inline label. Use the shared responsive/high-density floating-label size and preserve Light/Dark surfaces, compact geometry, and one focus indicator.
- Auto CRUD number formatting uses `DisplayFormat` or explicit field `Format` consistently in grid cells, mobile cards, and generated editors. Resolve display/parsing culture from host-registered `FlatLocalizationOptions` (`OpxFlatUi:Localization:Culture`), falling back to `CurrentCulture` only when localization options are absent. Retain a decimal numeric keyboard hint, assign the original numeric property type, and keep native number-input behavior for unformatted fields.
- In two-column Auto CRUD forms, align an inline Boolean checkbox to the adjacent outlined control's center-line by applying the same 4px top rhythm. Do not enlarge the row, move the checkbox to the floating caption line, or introduce a separate fixed-height exception.
- Global paging defaults come from typed `OpxFlatUi:Grid` appsettings. Normalize `DefaultPageSize` and `PageSizes` to `1-500`, ensure the default appears in the choices, and construct `GridViewState` from `FlatGridOptions` before the initial load. Keep explicit `SetPageSize(...)` and `FlatPager.PageSizes` as page-level overrides. The native page-size select keeps a one-pixel border and a one-pixel keyboard focus outline; do not inherit the thicker generic focus ring or remove visible focus.
- Grid sort/filter glyphs stay compact while preserving accessible hit targets and labels.
- CRUD controls use `Margin.Dense`. Use `.flat-crud-form-grid`: two columns with `10px` column and `7px` row gaps on desktop/tablet; one column with a `6px` row gap at `600px` and below. Direct children of the editor body use a `7px` vertical gap. Fullscreen editor height must not stretch grid rows or controls; fields stay top-aligned at intrinsic height and unused space remains below the form.
- Every outlined field container owns one continuous theme-resolved surface across its value and adornment areas, including browser autofill. Input adornment wrappers, glyphs, and adornment icon buttons remain transparent, borderless, and shadowless on top of that shared surface so they never expose the page background or create a separate color block. Keep the selector scoped to input adornments so ordinary AppBar, toolbar, grid, and standalone icon buttons retain their own state styling.
- Login/auth password fields with a show/hide action use the shared `opx-password-visibility-field` class. The eye/eye-off icon is white (`#fff`) in resolved Dark/Night and dark (`#212529`) in resolved Light, including when the password is currently visible; do not derive this contrast from `InputType` because toggling changes it to text. Keep its background transparent and preserve an accessible button label/keyboard action.
- Browser-autofilled inputs, textareas, and selects must retain the resolved field background, foreground, and caret colors in Light, Dark/Night, and Auto. Apply the shared `:autofill`/`:-webkit-autofill` rule globally across hover, focus, and active states; never fix only Login or allow the browser credential tint to split the input from its adornment surface. Autofill styling must not change field height, padding, label geometry, outline, or disabled behavior.
- Application metadata and Login branding are initial-development baselines for every new host, not later page customizations. During host scaffolding, bind typed `OpxFlatUi:Application` appsettings through `FlatApplicationOptions` and provide `AppName`, `CompanyName`, `Author` (default `opx`), copyright, `LoginBrandBackgroundColor`, `LoginBrandBackgroundImageUrl`, `LoginBrandOverlayColor`, and `LoginBrandOverlayOpacity` from the start. Render one `<meta name="author" content="...">` in the host document `<head>` from `ResolvedAuthor`; this global document metadata covers every routed page, so do not duplicate it in individual Razor pages. `Logo` and `LogoUrl` are both optional; when both are blank, render no logo wrapper, fallback icon, or reserved gap. When configured, validate `LogoUrl` as a relative/HTTP(S) asset and keep the logo compact (`34px` desktop brand mark and `30px` form-title mark by default). Never hard-code these values in an authentication page. Allow a validated six-digit background color, optional relative/HTTP(S) image URL, validated overlay color, and overlay opacity clamped to `0-0.85`; render images as `<img>` rather than injecting configuration as raw CSS. Follow the operational reference pattern: split brand/form presentation on desktop, omit the duplicate top identity row on mobile, retain the configured AppName in the form heading, use `Welcome back, {CompanyName}` copy, keep submit single-flight, and disable fields while processing.
- Do not render a static `Protected sign-in`, `Sample only`, or security/integration banner below the Login form. Show validation and simulated/real authentication failures through the shared semantic Error MessageBox with generic credential wording. A static sample may define one explicit local credential pair, but production authentication/session handling remains host-owned and must not be implied by the template.
- A Not Found page uses `Not found` as the AppBar `PageTitle`, retains balanced page gutters (`16px` on mobile), and must not place its heading or explanatory copy directly against the content edge.
- CRUD modals are centered on desktop/wide tablet and always fullscreen on mobile. Fullscreen mobile geometry is enforced by the shared editor, cannot be disabled per page, and is independent from FAB/no-FAB content spacing. Outside-click close is an explicit parameter and defaults to off; every permitted dirty close path asks for confirmation. While an editor is open, arm a same-URL browser-history guard so the first Back attempt is consumed by the modal regardless of clean/dirty state, then request close through the same processing and dirty-confirmation guard. A blocked close must re-arm the guard and leave both modal and route unchanged; visible Back/Cancel must remove the guard without leaving a phantom history step. Back, Cancel, and permitted backdrop close return `OnResult(false)` and must not refresh or reset caller state. Only an `OnSubmit`/`SubmitHandler` completion without failure or cancellation returns `OnResult(true)`. For CRUD forms, `AutoRefreshOnSuccess=true` may invoke `OnRefreshRequested` after result `true`; use the caller's existing load pipeline rather than a browser hard reload, and never invoke it for result `false`.
- CRUD modal headers stay compact: use a `54px` desktop/wide-tablet minimum, a `56px` mobile minimum before safe-area expansion, and a `2px` mode/eyebrow-to-title gap. Preserve the Back button touch target and let the top safe area increase the actual mobile header height when required.

## Responsive and mobile

- At `900px` and below, operational tables use equivalent cards; Web desktop tables start above `900px`. Prefer two card columns from `601px` through `900px` and one column at `600px` and below.
- Responsive record cards keep a `1px solid` outer border so each record remains a distinct object. Separators inside one record—header-to-body, fact rows/columns, references, progress, and action footer—use `1px dotted` borders. Remove duplicate final dividers so the outer record border remains the closing edge.
- Search/filter text controls are full width on mobile and may not be clipped. The icon action row follows the search row.
- No-FAB pages use `no-mobile-fab` and preserve `16px` top, left, right, and bottom gutters.
- FAB pages use `has-mobile-fab` and reserve safe-area-aware bottom space. The final content and internal scroll region stay at least `16px` above the FAB.
- Panel height is viewport/AppBar/safe-area aware and scrolls internally. Do not use preceding empty/action blocks that invalidate its mobile height calculation.
- On Web desktop, `FlatDataGrid` owns one bounded `.flat-data-grid-scroll` region with `overflow:auto`. Vertical overflow appears when rows exceed the available panel body; horizontal overflow appears when intrinsic column width exceeds the panel. A direct `div` host inside `.module-panel` that contains `.flat-data-grid-shell` is automatically made shrinkable above `900px` and hidden when the equivalent `.mobile-grid-list` is active at `900px` and below, regardless of the host's custom class name. Keep the toolbar and pager outside this scroll region, preserve sticky headers, and never nest competing grid scrollers or suppress the themed native scrollbars. Grid scrollbar thumbs use normal width and clear theme-resolved contrast; do not use a thin border-colored thumb that appears absent in Dark/Night. Document-level modal scroll locking must not change the internal grid overflow contract.
- Responsive grid switching must be reversible during live window resize without a reload. Crossing from above `900px` to `900px` or below hides the table and shows equivalent cards; crossing back restores the table and both internal scroll axes. Preserve the same rows and query/filter/sort/paging state, recompute the bounded grid height when viewport height changes, and never introduce document-level horizontal overflow.
- Mobile pager record summary and controls stay on one top-aligned, non-wrapping row when they fit.
- Pull-to-refresh is off by default. Enable it only with both `PullToRefreshEnabled="true"` and a real `OnRefresh` handler on an eligible data/list/monitoring/report/feed page. Start only when both the document and page-owned primary mobile scroll region are at the top. Auto-recognize `.mobile-grid-list`; use `PullToRefreshScrollSelector` for another primary region. Use the shared native-like gesture and indicator: vertical direction lock, finger-following resistance, pull/release/refresh states, a briefly guaranteed held refreshing position, and animated snap-back. Use non-passive move cancellation only after a downward pull is active; exclude incidental nested scrollers plus editor, overlay, popover, input/button, and FAB targets. Keep refresh single-flight, cooldown-protected, disposable, and query-state preserving; do not create a page-local pull indicator.
- Native MAUI behavior requires emulator/device verification; browser breakpoints prove Web DOM/CSS only.

## Theme and controls

- The built-in `blue` palette uses reference Primary `#004a77` for enabled Filled Primary controls in both Light and Dark/Night. Keep white foreground on the filled surface; use Light hover/subtle/emphasis `#003a5e`/`#e1f1fa`/`#003652` and Dark/Night hover/subtle/emphasis `#006da8`/`#102d3f`/`#c2e7ff`. Apply the family through shared palette tokens and typed display options, never as a page-local button override. Consumer-defined appsettings palettes may intentionally replace it.
- The OPX default base font size is `14.5px`, configured through `OpxFlatUi:Display:DefaultFontSizePx` and bounded by the host minimum/maximum. Density may change control rhythm but must not silently replace this baseline; persisted user overrides still win until Restore application defaults clears them.
- The Font size setting scales every textual surface from that baseline, including shell, AppBar, navigation, Settings, pages, grids, cards, dialogs, menus, and reusable components. Keep icon sizes and density-owned spacing/control geometry fixed; a font-size preview must not silently select or mutate another spacing preset.
- Light, Dark/Night, Auto, density, font size, navigation layout, and color-palette settings preview immediately. Save persists the user override; Cancel restores the prior value; Restore clears the override and returns to appsettings defaults. `Auto` must resolve `prefers-color-scheme` before first paint through the library bootstrap loaded in `<head>` before stylesheets, then react to later device-theme changes without reload; startup may not flash the Light background on a dark device. Root first-paint classes are isolated as `opx-root-theme-light`/`opx-root-theme-dark`, while reusable components use the resolved shell `theme-light`/`theme-dark` class. Never put the component `theme-dark` class on `<html>` because it leaks Dark descendant rules into an explicitly Light shell. Root, shell, `color-scheme`, background, cards, controls, portals, and theme-color must switch as one coherent resolved theme.
- Enabled and disabled buttons must remain visibly distinct on touch/mobile as well as desktop, especially in Dark/Night. Standard/Default, Primary, Secondary, Tertiary, Info, Success, Warning, Error, and Dark retain their semantic family. Enabled Filled buttons use a strong solid family color and enabled Outlined/Text buttons use a readable family foreground; disabled variants use a substantially quieter, desaturated family tint, border, and foreground without collapsing to one neutral gray.
