## UI/UX requirements analysis

- Accept the user's business intent as a sufficient prompt through `.agents/PROMPTING.md`; do not require PageId, component names, route, columns, breakpoints, or layout instructions. Infer routine UI decisions from the canonical registries and sample. Ask at most one focused question only when the answer materially changes workflow, ownership, permissions, transaction risk, or native capability.

- Before choosing a page or component, identify the user or role, primary job-to-be-done, information hierarchy, data density, frequent and critical actions, mutation/destructive risk, permissions, host/device/input context, interruption/offline constraints, loading/empty/error/disabled/success/unsaved/recovery states, accessibility, localization/RTL, and responsive needs.
- Select one canonical `PageId`, nearest sample archetype, shell, navigation, shared components, and interaction/state model from that analysis. Prefer the simplest composition that completes the user's job; never add dashboards, filters, CRUD, FABs, dialogs, or visualizations solely because a sample contains them.
- Package-first reuse is mandatory. Before creating markup, a component, CSS/JavaScript behavior, or a host adapter, inspect the supported NuGet public API and the mapped compiled canonical sample. If the capability exists, use it through its documented public seam; do not duplicate it locally, fork package CSS/JavaScript, or substitute a package-source `ProjectReference`. If it is genuinely absent, classify it first: a domain-neutral reusable need becomes a decision-ready package suggestion, while domain, authorization, persistence, integration, or native-platform behavior remains a host-owned seam. State the need, proposed API/component or integration shape, impact, priority, compatibility/testing/release boundary, and request approval before changing or publishing the package. Use `belum terklasifikasi` while availability or ownership is still unproven.
- Responsive CRUD/list cards must use the package component and canonical card contract when available: render the collection through `FlatMobileGrid`, keep each record root as `article.mobile-card`, and use the mapped canonical facts/body and action-footer classes. Never replace that structure with a bare manual `div.mobile-grid-list`, a classless `<article>`, or local card CSS. Package selectors intentionally own header/body padding, title-metadata separation, status alignment, responsive columns, scrolling, and touch behavior; missing a required canonical class is `bug integrasi aplikasi`, not a package spacing defect.
- Act as UI/UX, business, and data analyst when selecting dashboards, layouts, and transaction workspaces. Tie every KPI or chart to a business decision, identify data grain/source/freshness/units and drill-down, and map relevant transaction lifecycle, validation, approval, reversal/recovery, concurrency, and audit states. Never invent formulas, thresholds, statuses, permissions, accounting effects, or live data.
- For ERP, HR, and enterprise requests, read `.agents/skills/opx-flat-ui-development/references/enterprise-domain-layout-decision.md` and choose the dominant operating mode before the component: overview/decision, work queue, master data, transaction/document, approval/review, planning/scheduling, analysis/reporting, or setup/governance. Separate employee self-service, HR administration, manager approval, attendance/timesheet, payroll/compensation, and recruitment; preserve privacy and role boundaries. The agent decides the routine canonical layout, while policy, formulas, approvals, accounting/inventory consequences, authorization, persistence, and audit remain host-owned.
- Ask one focused question only when alternatives materially change workflow, data ownership, permissions, or mobile behavior. Otherwise document the assumptions and explain the selected pattern briefly. Domain data, authorization, persistence, and integrations remain host-owned.
- When analysis finds a material usability, accessibility, responsive, workflow, data-quality, performance, consistency, or recovery improvement, report it proactively as `Saran UI/UX` with the need/risk, one concrete canonical recommendation, user/business impact, priority (`Wajib`, `Disarankan`, or `Opsional`), and scope/approval boundary. ## Adaptive responsive design

- Responsive OPX UI is adaptive, not a desktop composition scaled down. Preserve one Blazor codebase and one design system, but deliberately transform information hierarchy, navigation, layout, actions, forms, and data presentation for the available viewport.
- Keep the established OPX boundaries authoritative: desktop/table behavior above `900px`, responsive/card behavior at `900px` and below, two-column cards from `601px` through `900px`, and phone/single-column refinement at `600px` and below. Component-specific boundaries already documented by the source of truth remain valid. Do not replace them with generic `768px`/`1200px` breakpoints.
- `FlatAppShell` Bottom mode resolves navigation from viewport width only. `BottomNavigationMaxWidthPx` defaults to `600`; this template intentionally sets `900` so tablet and phone widths use Bottom navigation while wider windows use the sidebar. Apply the chosen threshold identically to Web, MAUI Hybrid, and resized Windows desktop windows. Never branch this composition by OS, device type, user agent, or MAUI platform detection.
- When a user asks for Bottom navigation without naming how parent/overflow children open, choose the package `Sheet` presentation and set `OpxFlatUi:Display:DefaultBottomNavigationChildPresentation="Sheet"`. Use `MainView` only when explicitly requested or inside a clearly labeled showcase preview. The shared recursive navigation tree, active state, safe area, Back/Close behavior, and leaf navigation remain identical.
- Bottom-navigation labels must preserve descenders with the package-owned `1.25` line-height and `1px` bottom inset. Keep single-line ellipsis and the established `60px` bar; do not clip `g`, `j`, `p`, `q`, or `y`, enlarge the bar, or add an app-local override.
- Use viewport media/container behavior for typography and layout; never use Android/iOS user-agent detection to choose font size, spacing, or page composition. Native capability checks remain valid only for platform-owned features such as camera, notifications, safe area, keyboard/IME, or system Back.
- Android MAUI hosts that merge the status bar with the AppBar must follow `samples/Opx.MudBlazor.FlatUi.MauiHost.Sample`: attach host-owned `CommunityToolkit.Maui` `StatusBarBehavior`, keep the native bar transparent, measure the actual `WindowInsets` top inset, render the AppBar at `60px + inset` with controls centered in the lower `60px`, and update contrast-aware status icons after Light/Dark/Auto, system-theme, or palette changes. Do not hardcode the inset or apply native geometry to Web/Windows.
- Keep all canonical cross-host routes only in `samples/Opx.MudBlazor.FlatUi.Showcase`. Web and MAUI load it through `Router.AdditionalAssemblies` and use the same `ShowcaseNavigationCatalog`; executable hosts contain only runtime shell, adapters, and documented native-only diagnostic pages. The MAUI host starts Light with the static and interactive `Memuat` handoff, catches startup failures inside the OPX provider shell, and must not expose the default English Blazor loading/error surface.
- Do not show the stock .NET/MAUI splash artwork. Keep the unavoidable Android 12+ system splash as a neutral `#FFFFFF` surface with one-pixel white-on-white invisible artwork, then hand off directly to the canonical theme-aware `Memuat` loader. A system splash frame cannot be removed on every supported Android version; the contract removes branding/artwork and visual discontinuity rather than making a false zero-frame claim.
- Use `/maui-performance` for actual startup checkpoints and first completed route renders. Compare repeated Release runs on the same target hardware; never treat build duration, browser timing, or one device run as proof of Android/iOS performance generally.
- Derive text, controls, spacing, page gutters, and card rhythm from shared OPX tokens and typed display options. Default typography ownership and face to Device: with `UseAppFontSize=false`, ordinary UI inherits the device/browser system UI font stack and `1rem` plus accessibility scaling. Do not bundle, download, or force an app/custom font, and do not set a page-local ordinary `font-family`. Manual is an explicit bounded `16px` size override and does not replace the system font family; package numeric, code, and icon tokens remain intentional exceptions. Preserve semantic operational/supporting/metadata hierarchy, density independence, and high-density touch settings. Do not introduce page-local font scales or hardcoded repeated control heights merely to make one viewport look correct.
