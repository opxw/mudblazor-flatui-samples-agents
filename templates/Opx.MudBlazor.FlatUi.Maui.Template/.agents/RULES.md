## Adaptive responsive principle

- Build one Blazor codebase and one OPX design system, but adapt navigation, hierarchy, actions, forms, grids, and information density by viewport. Never treat mobile as a uniformly shrunken desktop screen.
- Preserve canonical OPX boundaries and tokens: `900px` is the desktop/table to responsive/card boundary, `601-900px` supports two-column cards, `600px` and below is the phone/single-column refinement, and Device is the default typography owner. With `UseAppFontSize=false`, ordinary UI inherits the device/browser system UI font stack and `1rem` accessibility scale; consumers must not bundle, download, or force an app/custom font or set page-local ordinary `font-family`. Manual is an explicit size override with a `16px` baseline and does not replace the system font family. Package numeric, code, and icon tokens remain intentional exceptions. Do not substitute generic `768px`/`1200px` breakpoints or page-local font scales.
- In `FlatAppShell` Bottom navigation mode, use viewport width as the only composition signal. `BottomNavigationMaxWidthPx` defaults to `600`; this template explicitly sets it to `900`. Above the configured value render the sidebar, and at or below it render Bottom navigation. Web, MAUI Hybrid, and a resized Windows EXE follow the same live-resize rule; OS, device-type, user-agent, and MAUI-platform detection are forbidden for this choice.
- A prompt requesting Bottom navigation implicitly selects `DefaultBottomNavigationChildPresentation="Sheet"`. Do not choose `MainView` unless the user explicitly requests it or the route is a labeled MainView showcase. Reuse the same recursive navigation tree and package sheet; never build a page-local submenu sheet.
- Feed Sidebar and Bottom navigation from one recursive `FlatAppShell.NavigationItems` tree when supported. Use `Menu` only for a deliberate compatibility override; do not duplicate equivalent Web and MAUI menu definitions.
- Keep Bottom-navigation labels descender-safe with the package-owned `1.25` line-height and `1px` bottom inset while preserving single-line ellipsis and the `60px` bar. Never clip `g`, `j`, `p`, `q`, or `y`, enlarge the bar, or patch this reusable behavior in consumer CSS.
- Give ordinary content-panel bodies a positive logical horizontal inset: default `padding-inline:14px` desktop and `12px` at `<=900px`, unless the mapped sample defines another positive value. Readable content's left inset must never be zero. Edge-to-edge table/media shells may use outer `padding:0` only when their immediate readable children own the positive inset; use logical properties for RTL. On short landscape screens, keep content vertically scrollable and top-aligned, consolidate same-scope actions, and avoid a second full-width Refresh toolbar.
- Choose layout through CSS viewport/container behavior, not Android/iOS user-agent detection. Native capability detection is limited to platform-owned camera, notification, safe-area, keyboard/IME, lifecycle, and system-Back integration.
- Use shared semantic typography, density, control, spacing, gutter, and high-density touch settings. Mobile keeps primary content readable and touchable while secondary information may collapse, defer, or move to detail; desktop stays compact and data-oriented.
- The canonical spacing preset is package density `Default`: set `OpxFlatUi:Display:DefaultDensity="Default"`; never invent `DefaultSpacing`. Compact and Comfortable remain user choices, but Restore returns to Default. Density changes internal rhythm only and must not override page gutters, positive panel padding, safe areas, or mapped component spacing.
- Keep one shared query/selection/permission/loading/mutation state across desktop tables and responsive cards/lists. Use one Razor structure where semantics remain equivalent; use dedicated templates only when the information hierarchy must change.
- Verify desktop, responsive/tablet, phone, and no-reload live resize in Light/Dark/Auto, including text scaling, keyboard focus, touch geometry, scroll ownership, and zero accidental page overflow. MAUI behavior still requires emulator/device evidence.

## Source-first development

- Analyze the user or role, primary job, information hierarchy, data density, frequent/critical actions, mutation risk, permissions, device/input context, required states, accessibility, localization/RTL, and responsive needs before choosing a page or component. Derive the simplest fitting `PageId`, archetype, shell, shared components, and interaction model; do not add a dashboard, filter, CRUD flow, FAB, dialog, or visualization merely because it exists in the sample.
- Act as UI/UX, business, and data analyst for dashboard, layout, reporting, and transaction requests. Tie KPIs and charts to named decisions, establish data grain/source/freshness/units/comparison and drill-down, and map relevant transaction lifecycle, validation, approval, completion, cancellation/reversal, retry, concurrency, and audit states. Never fabricate business formulas, thresholds, statuses, permissions, accounting effects, or live data.
- Ask one focused question only when alternatives materially change workflow, data ownership, permissions, or mobile behavior. Otherwise state the assumptions and why the selected pattern fits. Keep domain data, authorization, persistence, and integrations host-owned.
- When analysis identifies a material usability, accessibility, responsive, workflow, data-quality, performance, consistency, or recovery improvement, communicate it proactively as `Saran UI/UX` with one concrete recommendation, user/business impact, priority (`Wajib`, `Disarankan`, or `Opsional`), and whether it is in scope or needs approval. Do not manufacture cosmetic filler, override explicit user decisions, invent business rules, or silently expand scope.
- Before implementing a requested layout, state a concise blueprint with user/job, `PageId`/archetype, shell/navigation, desktop regions, tablet/phone transformation, primary/secondary actions, essential states, and UX rationale. Infer ordinary layout details from the canonical sample when intent is sufficient; do not delegate standard OPX layout decisions back to the user.
- Resolve every page prompt through `.agents/skills/opx-flat-ui-development/references/page-registry.md`, then apply the PageId's one canonical profile from `showcase-behavior-registry.md` before choosing source. State the selected stable `PageId` during implementation. Infer ordinary CRUD, form, grid, spacing, responsive, accessibility, state, and ownership behavior from the profile; do not ask the user to choose what the contract already defines. Do not treat route text, profile, AppBar `PageTitle`, component filename, or permission key as interchangeable with `PageId`.
- Treat `samples/Opx.MudBlazor.FlatUi.Sample` as the page-development source of truth. Start from the nearest sample archetype and preserve its shell, state ownership, responsive switching, loading, modal result, toolbar, FAB, and theme behavior.
- Treat `src/Opx.MudBlazor.FlatUi` as the reusable-component source of truth. Reuse an existing component before adding page-local markup. Move a pattern into `src` only when it is genuinely domain-neutral and reusable.
- Package-first reuse is mandatory. Inspect the supported NuGet public API and mapped compiled sample before creating markup, CSS/JavaScript behavior, a component, or a host adapter. When a fitting package capability exists, consume its documented public seam exactly; do not reimplement it locally, fork package assets, or replace NuGet with a package-source `ProjectReference`. When it is genuinely absent, classify ownership before proposing work: domain-neutral reusable behavior is a decision-ready package suggestion; domain, authorization, persistence, integration, and native-platform behavior stays host-owned. State need, proposed API/component or host seam, impact, priority, compatibility/testing/release boundary, and ask for approval before changing or publishing the package. If availability or ownership is not proven, say `belum terklasifikasi` and name the missing inspection.
- For responsive CRUD/list cards, use `FlatMobileGrid` and the mapped canonical card structure. Each card root keeps `article.mobile-card`; its facts/body and footer use the archetype classes already provided by package/sample. Do not hand-build `div.mobile-grid-list`, omit `mobile-card`, or introduce local card geometry CSS. Those package selectors own card padding, name/metadata separation, status/actions alignment, responsive grid columns, scroll ownership, and touch behavior.
- Bootstrap NuGet-only Blazor Web consumers through the repository `opx-flatui-web` template. Preserve schema `3.1`, `Opx.MudBlazor.FlatUi` `2.0.20`, `MudBlazor` `9.9.0`, public `PackageReference` mode, canonical `PageId`/archetype, host registrations, asset order, Light default theme, built-in `fluent-blue` default palette, Device/Manual font ownership, CRUD terminology, adaptive responsive rules, native-mobile deployment requirements, root-before-Router startup access gate, and baseline display settings. During checking, initialize display preferences, resolve theme/palette, and wrap configured `FlatSessionRestore` startup copy in the loading-only `FlatMudProviders` branch; create `Router` only after validation and do not nest this provider with layout providers. Run `audit_flat_ui_consumer.ps1 -ExactSample` before accepting exact sample output.
- When the user asks for the same, exact, canonical, source-of-truth, or sample-matching UI, read `skills/opx-flat-ui-development/references/exact-sample-mode.md`, generate the matching template, and establish an unchanged `-ExactSample` audit baseline before host integration.
- Diagnose package versus consumer ownership by comparing the consumer with an unchanged canonical sample on the same supported NuGet version. A proven package-owned component/API/CSS/JavaScript defect must be labeled exactly **"bug package"**. A consumer markup, local CSS, configuration, host service, stale asset, or integration defect must be labeled **"bug integrasi aplikasi"**. If evidence is incomplete, label it **"belum terklasifikasi"** and state the missing comparison; never guess from symptom location.
- Bootstrap new Android/iOS Blazor Hybrid consumers through `dotnet new opx-flatui-maui`. Keep its mobile contract, package-only CSS, CommunityToolkit registration and `StatusBarBehavior`, exact AppBar/status-bar theme bridge, Device typography, native no-bounce handler, textbox-only selection, static and interactive `Memuat` handoff, Settings, Bottom/sidebar shell, and root-before-Router authorization gate. Run `scripts/audit_maui_consumer.ps1` and an Android Release build; do not claim iOS native completion without macOS simulator/device evidence.
- A full MAUI page showroom and route-performance comparison belongs to `samples/Opx.MudBlazor.FlatUi.MauiHost.Sample`, where sync/audit tooling keeps every canonical Web route aligned. Do not inflate a normal generated consumer with the entire showroom unless explicitly requested.
- Every consumer host document emits exactly one `<!-- Powered by opx (github.com/opxw) -->` through `MarkupString` immediately inside `<body>` before `RootStartupGate`; literal Razor-file HTML comments and Razor comments are removed during compilation, so verify the initial HTTP response on multiple routes.
- Start a generated consumer with `run-clean.ps1`, which removes only its verified project-local `bin`/`obj`, restores, and runs without a second restore. Load reusable OPX and MudBlazor CSS only through their NuGet `_content` assets; reject local package-CSS copies, additional UI-framework imports/references, and the unused Bootstrap distribution in generated output. Keep `app.css` as the exact initial source-sample composition layer, never as a reusable component override.
- Treat Settings and sidebar navigation as mandatory initialization surfaces. Keep `MainLayout.razor` wired to the `MoreVert` AppBar menu, dedicated Application preferences modal, and Light/Dark/Auto choices; mount `SampleSidebarMenu.razor` with Dashboard `/`, default sample groups, search, and active-route expansion. Consumers may replace sample labels/routes with authorized domain navigation, but may not ship an admin shell without Settings or a functional sidebar.
- Keep sample domain content outside the reusable contract: dashboard status/quick-access widgets, user-summary records, current-user avatar/name/role, logout/session behavior, and final business menu labels/routes/permissions are host-owned. Audits may require the shell mechanism and initialized seed, but must not freeze example identities, counts, records, or business authorization as canonical data.
- Never copy sample business wording or static records into a reusable component. Samples may demonstrate IT, ERP, ecommerce, content, and operations; shared APIs remain domain-neutral.
- Business composition controls must inherit the package operational/supporting/metadata typography tokens. Keep body/control text normal weight and reserve semibold for hierarchy headings; mobile changes touch geometry, not typography hierarchy.
- Keep traceability, BOM/routing, rule, approval, attachment, recurrence, query, and comparison state controlled by the host through typed models and exact callbacks.
- Do not create a new page from memory when a matching sample exists. Read the sample and the components it invokes before editing.

## New or changed pages

- Large-record lookup forms use `FlatEntityLookup<TItem>` in the shared medium modal on desktop/wide tablet and the mandatory fullscreen modal on mobile. Render lookup candidates in one internally scrolling table grid. Reuse `GridColumnDefinition`; header interaction is ASC/DESC sort only, and search applies only to the currently sorted column while showing its label. Autofocus the search input on every lookup open; when another lookup control owns focus, unmodified letter/number typing appends to search and returns focus there without intercepting shortcuts or duplicating input-originated keys. Use supporting typography for search/record values and metadata typography for headers/descriptions, with bounded responsive scaling below `900px` while preserving touch heights. Render the closed trigger's selected/content value slightly below supporting size at normal `400` weight, never bold by default. Keep dotted row/cell separators, formatted/numeric alignment, a non-color-only candidate indicator, and no document overflow. Omitted columns fall back compatibly to `ItemText`/`ItemDescription`.
- Bind `FlatEntityLookup<TItem>.Items` from `IEnumerable<TItem>` so arrays, lists, collections, observable collections, and materialized projections work without adapters. Keep remote loading, authorization, query bounds, paging, mutation notification, and API errors host-owned; do not pass a live database query to the UI.
- Set `FlatEntityLookup<TItem>.ItemKey` for API-backed or replaceable records. Use `MultiSelect`, `SelectedItems`, and checkbox rows for many-value lookup; the confirmed `ItemsSelected` result must contain canonical items from the current `Items` snapshot so stale object instances do not leak to callers.

- Register every new route with one unique `opx.page.<area>.<purpose>` ID, canonical page name, prompt cues, shell/archetype, and source file. Preserve existing IDs through display-title changes. If a component has multiple routes, register each route separately. Keep the registry, source-map, navigation/title/search entries, and audit synchronized.
- Public Job Landing pages use `WebsiteLayout` and compose search hero, process, categories, job results, employer proof, CTA, and footer. Preserve semantic headings, labeled search controls, responsive one-column mobile layout, touch targets, and no document overflow. Keep vacancy APIs, applicant identity, resume scanning, consent, workflow, analytics, notification delivery, retention, and persistence host-owned.

- Compose disclosure/FAQ/settings sections with `FlatAccordion` and `FlatAccordionItem`; preserve textual titles, full-header keyboard/touch targets, `aria-expanded`, single-open default, explicit Multiple mode, optional Flush/leading/toggle icons, disabled contrast, and Light/Dark parity. Keep loading, authorization, persistence, and content security host-owned.

- On Kanban tablet/mobile, keep only full-width search and icon actions in the toolbar; move Assignee, Priority, and other structured filters into the shared `BottomSheet` with staged Apply/Reset and discard-on-close behavior. Desktop filters remain inline.
- For catalog, product, inventory, or other filter-heavy result pages, use `FlatFilterWorkspace`: show a bounded filter rail beside the desktop result, then hide the rail at `900px` and below and expose the same staged controls through its icon-only filter `BottomSheet`. Keep status tabs and search in the result toolbar, render `FlatDataGrid` plus equivalent mobile cards from one query state, commit mobile filters only on Apply, and discard staged changes on close/backdrop/swipe. Query execution, Add/Edit, authorization, and persistence remain host-owned.
- Use `FlatProductDetail` for media-heavy product/item details and `FlatProductMetric` for summary facts. Desktop uses a gallery/summary split; tablet/mobile stacks at `900px` without document overflow. Supply gallery, thumbnails, metadata, rating, metrics, variants, description, tabs, and actions through slots. Media delivery, pricing, inventory, reviews, authorization, edit persistence, and checkout remain host-owned.
- Use `FlatEditorWorkspace` and `FlatEditorSection` for large create/edit pages. Keep main fields/gallery/inventory in the broad desktop column and publish/schedule/category/tags in the compact rail; stack both at `900px` and below without document overflow. Reuse `FlatFileUpload` and `FlatMultiSelect<T>`. Rich-text integration, sanitization, validation, media storage/scanning, scheduling, authorization, concurrency, and persistence remain host-owned.
- Compose CRM/deal pipelines from `FlatKanbanBoard<TItem>` with `FlatKanbanBoardVariant.Pipeline`, typed `ColumnHeaderTemplate`, and `FlatPipelineCard`; never duplicate movement/filter infrastructure. The host computes aggregates and owns actions, authorization, persistence, and realtime state. Desktop scrolls five-plus stages internally; tablet/mobile stack them at `900px` and below without document overflow.

- Register an exact route, route-aware `PageTitle`, sidebar item, horizontal navigation/search entry where applicable, and permission boundary owned by the host.
- Keep PageId `opx.page.reference.development-rules` at `/development-rules` synchronized with accepted repository and skill contracts so developers can inspect the current summary in the executable sample. Canonical detail remains in the source rule and skill files.
- Do not render a duplicate page title or description by default. The AppBar owns `AppName` and current `PageTitle`. At the Manual `16px` baseline, keep their shared compact proportions near `12px` bold and `11px` regular; density presets must preserve those ratios.
- Use `FlatPage` for operational pages. Keep grid actions in its toolbar and hide unavailable actions. Standard writable CRUD pages define their single create action once with the `PrimaryAction*` parameters and `OnPrimaryAction`; `FlatPage` automatically produces the desktop button and icon-only mobile FAB without duplicate markup or an empty responsive action row.
- Mobile toolbars with at least two actions use one transparent inline utility Show/Hide button: Apps/action-grid while collapsed and Close while expanded, never a combo-box-like chevron or overflow menu. When `.module-search` exists, overlay it at the right edge, vertically center the complete touch target against the rendered search border box, and reserve input padding so collapsed actions consume no additional row; expanded icon actions render below. Preserve `aria-expanded`, explicit labels, full-width search, and permanently visible desktop actions.
- Use desktop tables above `900px` and equivalent responsive cards at `900px` and below; preserve one shared query/filter/sort/paging state. The switch must remain reversible during live window resize without reload, restore both internal table scroll axes when returning to desktop, and never create document-level horizontal overflow.
- Bind first empty requests to `FlatPage.InitialLoading`; the package chooses a responsive skeleton from `FlatPageKind`. Override with `SkeletonTemplate` or `LoadingContent` only when automatic geometry does not match, and keep global defaults in `OpxFlatUi:Loading`. Skeletons are initial-empty-state feedback only; refresh, filter, paging, sort, and CRUD reload keep current data visible and use the shared AppBar loading line.
- Desktop `FlatDataGrid` owns a single bounded two-axis scroll region. A direct `div` wrapper under `.module-panel` may use any host class; the package makes it shrinkable on desktop and hides it when the equivalent mobile grid is active. Keep toolbar and pager outside the grid scroll region, let intrinsic wide columns create horizontal overflow, let excess rows create vertical overflow, and do not add a second active scroller around the component. Use a normal-width, clearly contrasted theme-resolved thumb on both axes; a thin border-colored thumb is treated as visually missing in Dark/Night.
- Upload, showcase, documentation, and long-form pages use natural document scrolling, not the fixed-height `.module-panel` overflow contract. Reserve bounded internal scrolling for grids and intentional workspaces so previews, validation, and actions cannot be clipped.
- For table grids, derive default filters from the grid's `GridColumnDefinition` collection. Desktop headers and `MobileGridFilterSheet` use the same `Columns` and exact `GridViewState`; toolbar Filter visibility follows `Columns.Any(column => column.FilterEnabled)`. Never create separate mobile filter metadata/state, and remove stale criteria when a column becomes unavailable. Desktop header filter controls and native option menus use compact readable 11px text at normal `400` weight without inherited uppercase/bold; mobile sheet typography remains independently touch-scaled. Numeric header filters keep numeric semantics while hiding native spinner controls, and focus uses one softened-Primary one-pixel border without a second outline/shadow.
- Grid columns support proportional `WidthPercent` and fixed `WidthPx`, with pixels taking precedence when both are supplied. `WordWrap` is opt-in per column and defaults false; if one column wraps, top-align all cells in the row geometry. Detect or declare numeric/currency columns, align their headers/cells right, render numeric cell values with the shared monospace numeric stack plus tabular digits, and format through `FlatLocalizationOptions`. Infer the default from the CLR type: integer types and nullable integer types use `#,##0`; decimal/floating-point types use configured decimal precision. Do not render synthetic `.00` digits for an integer field unless the host explicitly requests them. Keep header labels in the normal UI font. Non-property keys use `ValueSelector`, custom templates use `FormattedValue`, and mobile cards reuse `FlatValueFormatter`.
- In bounded `FlatModelCrud` tablet/mobile layouts, make `.flat-model-crud-mobile` the only vertical scroll owner. Keep toolbar and pager outside it, reuse the visible theme-synchronized grid scrollbar, and prevent document-level horizontal overflow during resize.
- Use `FlatStatusChip` for reusable grid/card statuses: solid semantic flat background, readable foreground, square corners, no border/shadow, and no decorative bullet. Keep visible text or an accessible label so color is not the only cue. Mobile status cards may opt into `mobile-card-edge-tag`; give the direct header chip a fixed responsive width and overlap the top/right card border by exactly one CSS pixel, reserve non-overlapping title space, support short two-line status copy, and preserve zero document overflow.
- Shared geometry keeps cards, panels, inputs, dialogs, popovers, snackbars, menus, grids, toolbars, and reusable workspaces at `border-radius: 0`. Ordinary buttons default to `7px` through the bounded global `DefaultRoundedSizePx` setting (`0-12`); the package also applies this value to bottom-sheet top corners. Never add page-local rounded overrides. Semantic circles and FAB shape remain separate contracts.
- Use built-in `fluent-blue` as `DefaultColorPalette` with the package-owned Light accent family `#0067c0`, `#00549e`, and `#e3f2fe`; preserve its Dark/Night counterpart. Settings may persist another palette, but Restore returns to `fluent-blue`. Never reproduce palette colors in page-local CSS.
- Resolve widget/dashboard-card spacing to PageId `opx.page.reference.widgets`, `Widgets.razor`, and `docs/WIDGETS.md`. The parent grid owns `gap` (`12px` desktop, `10px` at `<=600px`); each widget keeps zero outer margin. Preserve body `12px`, header `9px 12px`, footer `8px 12px`, section `18px` desktop/`16px` mobile, heading-bottom `8px`, action-metric `13px` desktop/`12px` mobile, compact-metric `13px`, and lower-grid top `12px` desktop/`10px` mobile. Never create spacing by combining widget margins with grid gap or by padding both parent and child at the same boundary.
- Bind global paging defaults from typed `OpxFlatUi:Grid` appsettings and construct `GridViewState` from `FlatGridOptions` before initial loading. Keep page-specific page size and pager choices as explicit overrides. Keep the native page-size select focus as exactly one softened-Primary one-pixel border, with no outer outline, shadow, or double box.
- Use `FlatEditableGrid<TItem>` for inline Add/Edit/Delete. Keep one cloned draft and prefer `SaveRow` with `FlatGridEditResult<TItem>` so generated IDs/version values return as the canonical persisted row. Emit `RowResult` for every Create/Update/Delete success, failure, validation failure, and cancellation with the exact affected row. Retain failed operations in edit mode, discard Cancel without source mutation, and confirm Delete explicitly. Standard pages use `FlatPage.PrimaryAction*`; the grid Add toolbar is only for embedded grids. Switch to equivalent editor cards at `900px` and below. Authorization, collection mutation, persistence, concurrency, idempotency, and refresh remain host-owned.
- Generate ordinary flat model CRUD with `FlatModelCrud<TItem>`/`FlatModelForm<TItem>` and DataAnnotations or explicit typed field metadata. Use `Edit` consistently for the visible edit action, editor title verb, tooltip, and accessible label; do not replace it with `Ubah`. Use `FlatModelFieldKind.SearchComboBox` plus local `Options` or cancellable `SearchOptionsAsync` for lookup fields, and per-field `EditorTemplate` for any other visual component. Keep host ownership of authorization, API persistence/search bounds, canonical results, business validation, collection reload/mutation, confirmation, concurrency, and audit. On standard pages hide the component Add action and route `FlatPage` Add/FAB to `BeginCreateAsync`; only embedded CRUD may show local Add. Cancel leaves source/caller state unchanged; successful mutations emit `RowResult` and `Changed`.
- For a modal lookup inside Auto CRUD, declare a `Custom` field and render `FlatEntityLookup<TLookup>` through the shared `FieldTemplate`. Use stable lookup keys, support checkbox multi-select when required, map selected records to model keys in host code, and call the template context's `NotifyChanged` after mutation.
- A modal opened inside another editor uses form-less nested content and topmost-only history interception. Closing or pressing Back on the lookup must close only that lookup, never submit/cancel the parent form or discard its draft.
- Build visual generated-form layout with `FlatModelFormDesigner<TItem>` and PageId `opx.page.reference.model-form-designer`. Preserve drag/drop and Move up/down parity, one/two-column preview, stable field keys, validated class tokens, bounded `0..48px` spacing, Light/Dark parity, and a one-column mobile designer without page overflow. Native fields, searchable combos, image fields, and per-field custom visual editors must all retain the same layout wrapper and live-preview behavior. Feed the normalized layout to `FlatModelForm.Layout`/`FlatModelCrud.FormLayout`; host code owns authorization, class allowlists, persistence, versioning, concurrency, and audit. Keep wrapper emphasis transparent and limited to a restrained rail/keyline so it never replaces an input, combo, custom editor, or textarea theme surface.
- Auto CRUD text, numeric, date, select, and multiline editors default to one outlined floating label derived from metadata `Label`/`Display(Name)`. Keep `Placeholder`/`Display(Prompt)` as the optional hint inside the control, keep the required marker in the floating caption, and retain an inline label for checkboxes. The label background must compute to transparent in every theme; use only a two-pixel surface-matched pseudo-element to mask the outline behind the caption. Keep its line-height at least `1.2` so glyph ascenders/descenders are never clipped while the caption center stays on the outline. Match shared responsive/high-density typography; do not render a duplicate external label, rectangular label block, or second focus ring.
- Apply Auto CRUD numeric `DisplayFormat`/field `Format` to desktop grid, mobile cards, and the generated editor. Resolve culture from registered `FlatLocalizationOptions` (`OpxFlatUi:Localization:Culture`) and use `CurrentCulture` only as the missing-registration fallback. Return the original numeric property type, retain `inputmode="decimal"`, and keep native `type="number"` only when no format is configured.
- Use `FlatNumberInput` for standalone decimal fields requiring a floating label, right-aligned monospace/tabular value, and localized `#,##0` or `#,##0.00` formatting. Use `FlatNumberText` for matching read-only labels; built-in `FlatDataGrid` Number/Currency cells use it automatically and custom templates opt in explicitly. The input emits `decimal?`, formats initially and on blur/Enter, retains invalid text for correction, and leaves persistence/business validation to the host.
- Default every shared numeric surface to `Consolas` through `--opx-numeric-font-family`; hosts may replace that token globally, but page-local numeric font stacks are forbidden. Use `--opx-type-numeric` with tabular digits for values and keep `FlatInfoItem` facts at normal `400` weight.
- Align inline Boolean checkboxes in two-column Auto CRUD forms to the adjacent outlined control center-line with the same 4px top rhythm. Preserve the established 38px control height and intrinsic grid row height.
- Keep 16px mobile outer gutters. Use no-FAB bottom 16px or safe-area-aware FAB clearance as defined in root `RULES.md`.
- The operational AppBar uses a compact `60px` height. Vertically center its `40px` hamburger touch target so top and bottom gaps are both `10px`; title and trailing actions share that axis. In phone Bottom navigation, the hidden hamburger must not collapse AppBar content against the viewport; keep the toolbar at `16px` left/right gutters while preserving this `60px` rhythm.
- Mobile search/filter toolbars with two or more secondary actions keep the text field visible but default the icon-action row to collapsed/hidden (`MobileToolbarActionsExpandedByDefault=false`). The Apps/Close toggle remains accessible in the text field; desktop actions remain visible. Initial expansion is explicit opt-in only.
- Keep Bottom child navigation configurable through `DefaultBottomNavigationChildPresentation`: `Sheet` remains the default; `MainView` shows the current parent level as square icon-and-text tiles between the AppBar and bottom bar. Preserve recursive Back/Close, active state, safe areas, one internal scroller, and tablet/desktop sidebar fallback in both modes.
- Use `FlatFormModal`/`CrudEditorShell` for CRUD editors. Mobile editors are fullscreen; cancel/back returns false without refresh, while successful CRUD submit may refresh through the caller pipeline.
- Back precedence is modal/overlay first, then Blazor route history, then native host fallback. In MAUI Android, consume the first Back through `opxFlatModalHistory`, use WebView history for the next Back, and allow native app exit only when neither can handle it. Closing a modal must never immediately close the application.
- Enable pull-to-refresh only on eligible pages with a real handler. Reuse the shared native-style circular resistant gesture with progress-driven arrow, primary ready state, animated refresh arc, assistive status text, held refresh position, and snap-back; do not build page-local variants. Browser simulation is not native MAUI proof.
- For Android/iOS MAUI deployment, read `skills/opx-flat-ui-development/references/maui-mobile-deployment.md`. Require `CommunityToolkit.Maui`, `UseMauiCommunityToolkit()`, and Toolkit `StatusBarBehavior` on the native root page. Keep mobile typography in Device mode by default (`UseAppFontSize=false`) so device/browser `1rem` and accessibility scaling remain authoritative. Text-button labels and containers must accommodate that scale without clipping or reducing the minimum touch target; a fixed height that cannot grow with text is invalid.
